## 必修（阻擋合併）

### R1. 禮貌的請求被當成提問，交辦不出去（階段 2）

`src/workspace-chat.js` 的 `queryOrRefusal` 正規表示式太寬。驗收者實測，以下四句都會從 `new_work` 被降級成 `question`：

- 「可以幫我做一份 Q3 回顧簡報嗎？」
- 「幫我做簡報，例如放營收趨勢圖」
- 「請問你能幫我整理這三篇文章」
- 「幫我比較 A 和 B 供應商，看哪個比較好？」

目標使用者最常用的就是這類禮貌問句，所以這是主要入口壞掉。

修法：
- 移除以 `嗎？`、結尾問號、`請問`、`例如`、`是否` 等字詞判斷降級的寫法。
- 伺服器端只保留**明確的否定或撤回**，例如「不用幫我做」「我只是問問」「先別建立」。
- 其餘判斷交給 AI 的意圖分類。誤判的代價很低，因為提案卡本來就要使用者按「開始」才會建立任務。
- 新增測試：上面四句（用 fake runner 回傳 `new_work`）必須保留為 `new_work`；明確否定句必須被降級。

### R2. 提案卡的拆解和 AI 指派沒有保存（階段 2 → 3）

現在按「開始」時，`assignTask` 把提案攤平成一段文字塞進 `request`。每個步驟的負責 AI 因此遺失，多代理引擎拿不到這些資料。

修法：
- `POST /api/tasks` 接受結構化的 `proposal` 欄位，存入任務（例如 `planning.proposal`）。每個步驟包含 `title`、`purpose`、`agent`、`reason`。
- 伺服器驗證 `agent` 必須是已設定且可用的 provider（`codex`、`claude`、`copilot` 中、`diagnose` 判斷可用者）。不可用時改為該階段的預設 AI，並在任務訊息中告知使用者。
- 擬計畫（C 階段）的 prompt 必須帶入提案步驟，要求 AI 盡量沿用步驟拆成 `workItems`，並為每個工作項目記錄建議的 `agent`。
- 測試：提案中指派的 AI 會保存下來；不可用的 AI 會被替換並告知；C 階段 prompt 含有提案步驟。

### R3. 多代理引擎在介面上用不到（階段 3 → 4）

`POST /api/tasks/:id/runs`（`coach.queueRuns`）只有 API 和測試呼叫，網頁和自動模式都不會用到它。結果使用者在真實操作中永遠看不到多個 AI 同時工作，願景第 2 點無法達成。

修法：
- 計畫核准後，若有兩個以上沒有相依、可交給 AI 的工作項目，執行改走 `queueRuns`，以 R2 保存的 `agent` 作為各項目的指派。
  - 預設：「工作中」面板與任務詳情出現「開始製作（N 項可同時進行）」按鈕，使用者按一次就排入全部項目。
  - 自動模式（autopilot）開啟時直接排入，不需要按。
- 只有一個可執行項目時，沿用既有單代理流程即可。
- 前置項目完成並經使用者確認後，下游項目要自動排入（`confirm`／`confirm-all` 之後已呼叫 `driveRuns`，請確認下游項目確實被排入，而不只是重新驅動已排隊的項目）。
- **端對端測試（必要）**：用 fake CLI，經真實 HTTP API 走完整條路：
  1. 對話送出新工作，取得提案。
  2. 按開始，建立任務。
  3. 擬計畫，產生兩個獨立項目加一個相依項目。
  4. 核准計畫。
  5. 開始製作，兩個獨立項目同時處於 `running`。
  6. `GET /runs` 回傳三筆紀錄，其中一筆在等前置項目。
  7. 確認前兩項後，第三項開始。

### R4. 主對話不能指揮進行中的工作（階段 4）

主對話收到 `instruct` 意圖時，仍然只顯示「前往這個任務」。可以停止或改派的，是任務面板裡另一個靠正規表示式判斷的文字框，不在主對話中。

修法：
- 主對話的 `instruct` 回傳加上結構化動作：`{ action: "stop" | "reassign" | "change_scope", runId?, provider?, text? }`。伺服器驗證 `runId` 屬於該任務、`provider` 可用。
- 對話中顯示動作預覽和「確認」按鈕，確認後呼叫既有的 `/runs/:id/stop`、`retry`、`reassign`，或 `instruct` 的 dry-run → 確認流程。
- 面板內的指揮文字框可以保留，但要改成呼叫同一套 AI 意圖判斷，不要維持兩套規則。
- 測試：三種動作都要先預覽、經確認才執行；工作區資料中出現「停止全部工作」這類文字時不會觸發。

### R5. 簡報預覽和決策卡實際上不會出現（階段 6）

逐頁預覽要求成果是 `<section class="slide">` 結構，決策卡要求成果含 `mentor-decision` JSON 區塊。可是 `src/coach.js` 的製作 prompt 從未要求 AI 輸出這兩種格式，所以真實執行時這兩個功能幾乎不會觸發。

修法：
- 提案卡或任務的成果形式為「簡報」時，製作（D 階段）prompt 要求輸出單一 HTML，每頁一個 `<section class="slide">`，每頁一個 `<h1>`～`<h3>` 標題。
- 成果形式為「決策建議」時，要求成果內含 `mentor-decision` JSON 區塊，格式與 `parseDecisionCard` 一致。
- 自動檢查：簡報沒有 slide 區塊、決策建議缺少或無法解析 JSON 時，標示為「未通過」，並寫出白話原因。
- 測試：兩種成果形式的 D 階段 prompt 含有格式要求；fake CLI 產出的成果能被解析並顯示。

### R6. 數字來源檢查會把沒有來源的數字標成「有來源」（階段 6）

`checkNumberSources` 用 `source.includes(number)` 比對。驗收者實測：成果寫「20%」、素材寫「120%」，結果被判為「有來源」。這比漏報更糟，因為它製造了假的可信度。

修法：
- 改成**數字邊界比對**：前後不能緊接數字、小數點或千分位逗號。
- 比對前把雙方的千分位都正規化，例如「1,200」與「1200」視為相同。
- 單位不同時不算相符。
- 測試：20% 對 120% 判無來源；1,200 對 1200 判有來源；3 對 2030 判無來源。

### R7. 專案學習筆記露出工程代碼，回顧問題區塊有錯（階段 5）

- 「進度」表的狀態欄直接輸出 `TODO`、`REVIEWED`、`DONE` 等代碼。請改用白話：尚未開始、待你確認、已確認等，並沿用 `web/assets/plain-words.js` 的對照或在後端建立同一份對照。
- 「回顧問題」區塊無條件輸出「尚無使用者確認的回顧問題。」，有問題時也會出現。改成只在沒有問題時輸出。
- 程式碼中沒有任何地方會設定 `confirmedQuestion`，任務完成後也沒有「產生我學到的與回顧問題」的流程，這是規格項目。請補上：
  1. 任務完成後，使用者按一次按鈕，由 AI 產生候選。
  2. 使用者勾選要保留的項目。
  3. 只有勾選的項目寫入筆記；勾選「以後都要這樣做」的規則走既有學習流程。
- 筆記更新的 `onChanged` 目前只在 CLI 啟動的 `main` 中掛上。請改在 `createRequestHandler` 內設定，並補一個整合測試：經 HTTP 建立任務、核准計畫、完成工作、記錄決策後，筆記對應段落都有更新。
- `GET /api/tasks/:id/project-note` 目前會寫檔。請改成讀取時不寫檔（若需要寫入，改用 POST）。
