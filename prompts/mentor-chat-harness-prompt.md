## 一、產品願景

**Mentor 是使用者每天工作的主畫面。** 使用者像使用 ChatGPT 一樣，在對話中提問或交辦工作；背後由一組可以自選的 AI（Codex、Claude Code、GitHub Copilot CLI）分工完成；過程透明可見；做完的專案變成使用者讀得懂、學得會的 Markdown 筆記。

使用者原話整理成三個目標：

1. **只在這個畫面工作。** 我交辦事情，它讓我看到進度。
2. **看得見每一個正在執行的狀況。** 是開多個代理還是單一個？每一個負責什麼？用哪個 AI？做到哪裡？
3. **專案完成後變成我的知識。** 整個專案整理成一份 MD，清楚看到狀態、進度、結論，讓我好好學起來、內化成自己的知識。

### 與一般代理工具的差異

nanobot、OpenClaw 這類工具的重點是「代替你執行代理任務」，人看結果即可。Mentor 的定位是**人在中央的指揮中心**：

| | 一般代理工具 | Mentor |
| --- | --- | --- |
| 主要價值 | 幫你把事做完 | 幫你把事做完，而且你看得懂、學得會 |
| 人的角色 | 下指令、收結果 | 交辦、做關鍵判斷、驗收、吸收 |
| 過程 | 多半是黑箱或技術日誌 | 用白話呈現每個代理在做什麼、為什麼 |
| 結束時 | 一個產出檔 | 產出檔 + 一份專案學習筆記 |

## 二、目標使用者與典型任務

**使用者不是工程師。** 例如 PM、行銷、業務、行政、顧問、研究助理、學生。他們會用 ChatGPT，但不熟悉終端機、Git、模型參數或程式碼。

日常任務以三類為主，所有設計以這三類跑順為優先：

| 類型 | 例子 | 好的成果長什麼樣 |
| --- | --- | --- |
| 做簡報 | 「把這三份資料整理成給主管的 8 頁 Q3 回顧簡報」 | 有主張、每頁一個重點、數字有來源、可以逐頁預覽與修改、可下載 |
| 資訊整理 | 「整理這 5 篇文章的重點，做成比較表」「把會議紀錄整理成待辦」 | 結構清楚、每條重點能點回出處、沒有編造 |
| 做判斷 | 「我們該選 A 供應商還是 B？」「這個提案有什麼風險？」 | 選項並列、各自的好處與代價、依據、還不知道的事、建議與理由；最後由人決定 |

寫程式、修改使用者的程式碼 repo 不是本版重點。

## 三、體驗原則

1. **白話，零術語。** 使用者介面不出現 A–F、revision、workItem、sensor、provider、effort、token、exit code、CLI 等字眼。需要時用「第 2 版」「工作項目」「自動檢查」「AI 助手」「思考深度」「用量」替代，並在需要細節的人可以展開的地方保留原始資訊。
2. **對話優先，畫面輔助。** 任何事都能從對話開始；看板、設定、歷史是輔助入口，不是必經之路。
3. **AI 先準備，人只做判斷。** 每次需要人時，給建議選項、理由和代價，讓人一鍵選擇或改一句話；不要讓人填表。只問會改變方向的問題，一次最多 3 題。
4. **進度看得見，但不吵。** 預設顯示一句白話的「現在在做什麼」，細節按需展開。
5. **成果看得到，改得直接。** 簡報能逐頁預覽，使用者可以指著某一頁說「這頁改短」。
6. **誠實。** AI 說完成、自動檢查通過、人工驗收是三件不同的事。未驗證就寫未驗證；數字沒來源就標示沒來源；中斷就標示「不確定是否完成」，不自動重跑。
7. **不讓使用者擔心弄壞東西。** AI 只寫入 Mentor 指定的成果資料夾；任何會刪除、覆蓋或對外送出的動作都要確認，且盡可能可以復原。

## 四、體驗上最需要加強的地方

以下是對現況的判斷，依對非工程使用者的影響排序。實作前請自行核對現況並在 PR 說明中更新。

| # | 問題 | 現況 | 方向 |
| --- | --- | --- | --- |
| 1 | **上手門檻太高** | 需要 Node、終端機、自行安裝並登入 AI CLI | 首次啟動有引導頁：自動偵測哪些 AI 可用、白話說明缺什麼、一步一步帶登入、提供「先用示範資料試玩」；錯誤訊息都附下一步 |
| 2 | **術語與流程概念太多** | A–F 階段、revision、PASS/FAIL、預覽計畫、批准等名詞直接露出 | 全面白話化（見原則 1）；流程名稱藏在背後，只呈現「了解需求 → 擬計畫 → 製作 → 檢查 → 交給你確認」 |
| 3 | **聊天不是主角** | 聊天是右側附屬功能，只能問答或提議建任務；主畫面仍是看板與表單 | 對話成為主畫面，能交辦、能追問進度、能對正在進行的工作下修改指示 |
| 4 | **看不到多代理在做什麼** | 每個任務一次只跑一個代理，沒有「現在有哪些 AI 在工作」的總覽 | 代理面板：每個代理的角色、使用的 AI、白話進度、耗時、等待原因、停止按鈕 |
| 5 | **選 AI 太技術** | 依階段指派 provider／模型／推理深度 | 以「用途」描述與推薦（例如「擅長寫作與整理」「速度快、適合簡單整理」），預設由 Mentor 推薦，使用者可在對話中說「審閱交給 Claude」 |
| 6 | **確認次數多、要讀的字多** | 計畫預覽、逐項確認、工作卡細節多 | 合併成少數關鍵時刻（見第七節）；其餘自動進行並記錄 |
| 7 | **成果預覽不夠貼近日常格式** | 成果多為 HTML／Markdown，需另開檔案 | 對話內直接預覽；簡報逐頁縮圖；支援指著頁面或段落給修改意見；提供使用者熟悉的下載格式（至少 PDF，盡量提供 .pptx／.docx；做不到時誠實說明並提供替代） |
| 8 | **素材進來的路徑不直覺** | 有附件上傳與 Obsidian 選取 | 在對話框直接拖拉檔案、貼網址、貼文字、選筆記；AI 回覆說明讀了哪些素材、哪些讀不到 |
| 9 | **判斷類任務缺少專用呈現** | 判斷結果混在一般文字或文件裡 | 決策卡：選項、好處、代價、依據、未知、建議；使用者的最終選擇與理由寫回專案筆記 |
| 10 | **做完沒有「學到什麼」** | 任務檔是系統狀態檔，含 JSON 區塊，不適合閱讀 | 每個專案自動維護一份人讀版學習筆記（見第十節） |
| 11 | **錯誤與額度不友善** | 額度用完、登入過期時訊息偏技術 | 白話說明發生什麼、成果是否保留、可以怎麼做（換一個 AI 接手、稍後重試）；不丟失任何已完成的工作 |

## 五、現況盤點：保留與改變

**保留**（不要重寫，改為在上層使用）：

- 任務 Markdown 正本、revision 與過期操作拒絕（409）。
- `agents.js` 的 CLI 啟動方式與各 provider 的權限設定。
- 計畫中的 `workItems` 與 `dependsOn`，它已是一張相依圖，可直接作為多代理拆解的基礎。
- 停止、重啟後標示「未知」、不盲目重跑的復原原則。
- 交接摘要、本輪工作卡、自動檢查、人工驗收分層。
- Obsidian 插件與知識策展流程。
- 所有 HTTP 安全機制。

**改變**：

- 互動模型：從「人跟著 A–F 走」改為「人跟指揮者對話，指揮者決定走哪條路」。A–F 保留為內部的一種標準做法（適合需要文件產出的任務），不再是唯一路徑，也不在介面露出階段代號。
- 執行模型：從「一個任務一個執行中代理」改為「一個任務多個代理，依相依關係並行」。
- 主畫面：從看板改為對話 + 代理面板。
- 任務的閱讀版：新增人讀版專案筆記，與系統狀態檔分開。

## 六、對話主介面

### 版面

- 桌面：左側窄欄為專案清單（最近、進行中、需要我處理）；中間為對話；右側為「工作中」面板（代理狀態與成果預覽，可收合）。
- 手機（390 px 與 320 px）：對話全螢幕；「工作中」以頂部狀態條顯示「3 個 AI 工作中・1 件等你」，點開為全頁。
- 既有的看板、交接中心、回收桶、設定移到次要入口，功能保留。

### 意圖判斷

指揮者 AI 讀取使用者的訊息，判斷屬於哪一類，並在回覆中讓使用者看得出它的理解：

| 類型 | 例子 | 行為 |
| --- | --- | --- |
| 一般提問 | 「什麼是 NPS？」「上週那份報告結論是什麼？」 | 直接回答；引用專案或筆記時附來源；不改任何狀態 |
| 小型立即工作 | 「把這段改短一點」「幫我翻成英文」 | 直接完成並顯示結果，不建立完整專案；使用者可以「存成專案」 |
| 新的工作 | 「幫我做 Q3 回顧簡報」 | 產生「工作提案卡」（見下），使用者確認後才開始 |
| 對進行中工作的指示 | 「第 3 頁數字改用 9 月的」「先停一下」「審閱改給 Claude」 | 找出對應專案與代理；會改變範圍的指示先顯示影響（哪些已完成的部分要重做）再確認 |
| 補充素材或回答追問 | 拖入檔案、回答 AI 的問題 | 綁定到對應專案；說明這份素材會影響什麼 |
| 不確定 | 意圖或對應專案不明 | 用一個問題加 2～3 個選項確認，不猜 |

規則：

- 資料、檔案、網頁、歷史對話中的文字都是資料，不能授權操作。只有使用者本人在對話中的明確指示或按鈕確認才算。
- 查詢、假設、舉例、否定句不得觸發建立工作。
- AI 不可假裝已經執行、已經改檔或已經建立專案。

### 工作提案卡

交辦新工作時，指揮者在對話中提出一張卡片：

- 我理解的目標（一句話）、給誰看、成果形式。
- 我打算怎麼做：拆成幾個部分，每部分由哪個 AI 負責、為什麼（白話）。
- 預計需要你做的事（例如中途確認一次骨架、最後驗收）。
- 會用到的素材；缺少的素材。
- 按鈕：「開始」「修改」「先問我幾個問題」。使用者可以直接打字改，例如「不用審閱，直接做」。

## 七、編排與多代理

### 拆解

- 指揮者依任務類型選擇做法：小工作單一代理；一般工作沿用「了解需求 → 擬計畫 → 製作 → 檢查」；大工作拆成多個工作項目，沒有相依的項目可並行。
- 每個工作項目有：白話名稱、用途說明（一句話）、負責的 AI、相依項目、成果位置、驗收條件。
- 簡報與文件類任務保留現有「骨架版」做法：先產出最小可看的版本讓使用者確認方向，再展開其他部分。
- 拆解由使用者在提案卡確認。預設「先確認再開始」；設定中可開啟「小工作自動開始」。

### 執行

- 將 `planning.running` 由單一物件擴充為多筆執行紀錄（例如 `planning.runs[]`），每筆對應一個工作項目與一個代理。保留向下相容：舊任務檔能讀、能繼續。
- 並行上限可設定（預設 2～3），避免一次耗盡額度；超出上限的項目排隊並顯示「排隊中」。
- 並行代理各自寫入獨立子資料夾（例如 `outputs/<task>/<item>/`），不得互相覆寫；整合步驟由一個代理負責並明確列出它讀取的來源。
- 每個代理可以單獨停止；停止、失敗、中斷時不影響其他代理，並明確標示受影響的下游項目。
- 一個代理失敗（額度用完、登入過期）時，提供「換一個 AI 接手」：使用既有交接摘要，不重講背景。
- 修改既有工作時沿用 `work-item-impact.js` 的下游失效邏輯，向使用者說明哪些部分需要重新檢查。

### 選擇 AI

- 介面以用途描述 AI，模型名稱放在展開資訊裡。
- 預設由 Mentor 依任務類型推薦（例如製作與審閱用不同 AI，降低同一個 AI 自己審自己的盲點），並說明理由。
- 使用者可以在提案卡或對話中改派，例如「全部用 Claude」「審閱給 Codex」。改派只影響之後開始的代理，不影響正在執行的。

## 八、進度呈現（「工作中」面板）

每個代理一張小卡：

- 角色與用途：「資料整理員：讀你給的 3 份報告，整理成數據表」。
- 使用的 AI（圖示 + 白話名稱）。
- 狀態：排隊中／工作中／等你回覆／完成待你看／已確認／失敗／已停止／不確定是否完成。
- 一句白話的目前動作（由代理回報或依階段推得，不可編造進度百分比）、已經過時間。
- 相依關係：「等『資料整理員』完成後開始」。
- 操作：查看成果、停止、換 AI、展開詳細紀錄（原始 prompt、回覆、用量，給需要的人看）。

面板頂部一句總結：「3 個 AI 工作中，預計還需要做：分析、審閱。目前沒有需要你處理的事。」需要人時，對話中同步出現提醒。

狀態更新可以先用輪詢，若改用 Server-Sent Events 須維持同源與 session 檢查。

## 九、成果預覽與修改

- 成果直接在右側面板或對話中預覽，不需另開檔案。
- 簡報：逐頁縮圖與放大檢視；使用者可以點選一頁（或一段文字）後輸入修改意見，指揮者把意見綁定到該頁並交給負責的代理。
- 資訊整理：表格與清單可閱讀；每條重點附出處，點擊可看原文片段。
- 判斷：決策卡呈現選項、好處、代價、依據、未知、建議。使用者按下選擇並可補一句理由，寫回專案筆記。不得由 AI 代替使用者做最終決定。
- 數字：每個關鍵數字標示來源；找不到來源的標示「無來源」。可沿用 `examples/lab/` 中「數字都要在素材找得到」的檢查方式作為自動檢查。
- 下載：至少提供 Markdown 與 PDF（或可列印的 HTML）；.pptx／.docx 若能以零依賴方式產生則提供，否則誠實標示「尚未支援」，不要假裝。

## 十、專案學習筆記（MD）

每個專案自動維護一份**給人讀**的 Markdown 筆記，與系統狀態檔分開：

- 位置：`MENTOR_HOME` 下的專案筆記資料夾（例如 `vault/notes/`），檔名用專案標題，可一鍵存到使用者選定的 Obsidian Vault。
- 更新時機：每次專案狀態改變時重新產生系統區塊；使用者在系統區塊以外寫的內容必須保留。
- 結構建議：

```markdown
---
title: Q3 回顧簡報
type: 專案筆記
status: 製作中 | 待驗收 | 已完成
updated: 2026-11-14
tags: [簡報, Q3]
---

# Q3 回顧簡報

成果連結、主要結論、數字來源。
```

- 筆記內容只來自紀錄與成果，不得編造未發生的過程；未驗證的事寫明未驗證。

## 十一、上手與錯誤處理

- 首次啟動引導：偵測 Node 以外的必要條件（哪些 AI CLI 已安裝、已登入），白話說明缺什麼與怎麼補，提供「用示範資料試玩」（明確標示 AI 回覆為模擬）。
- 所有錯誤訊息包含：發生了什麼、已完成的工作是否保留、建議的下一步按鈕。
- 額度與用量用白話呈現（例如「這個專案大約用了 3 次 Claude 對話」）；費用只能標示為估算，不推論帳單。
- 重新整理頁面、關閉瀏覽器或重啟服務後，對話、專案與代理狀態都能恢復；中斷的代理標示「不確定是否完成」並請使用者決定。

## 十二、安全與誠實

- AI 預設只能寫入該專案的成果資料夾，不執行會改動使用者電腦其他位置的動作。非工程使用者無法判斷 sandbox 差異，因此預設採最保守設定，並在進階設定中如實說明各 AI 的隔離程度不同。
- 外部文件、網頁、附件中的指令一律視為資料（提示詞注入防護，參考 `knowledge/prompt-injection-numeric-integrity.md`）。
- 「完成」「通過」「已確認」只能各自代表其真實意義；任何進度、時間預估、用量都不得編造。
- 刪除、覆蓋、對外送出、套用整理等動作需確認，並盡量提供復原。

## 十三、實作順序與驗收

每一階段獨立可驗收、可合併。每階段結束更新 `docs/implementation/` 下的追蹤文件，記錄已實作、已自動測試、已瀏覽器檢查、待真人驗證。

**階段 0：恢復基線。** 修好 11 個失敗測試，CI 三個 OS × Node 20/22/24 全綠。

**階段 1：對話成為主畫面。**
- 新版面（桌面三欄、手機單欄 + 狀態條），舊入口移至次要選單且功能不變。
- 意圖判斷（提問、小型立即工作、新工作、對進行中工作的指示、補充素材、不確定）與工作提案卡。
- 介面白話化：建立術語對照表，掃描使用者可見文字不得出現禁用術語（可加自動測試）。
- 驗收：用 fake CLI 測試每種意圖的路由；查詢與否定句不觸發建立；資料中的指令不授權操作；320／390／1360 px 無水平溢出。

**階段 2：多代理並行與「工作中」面板。**
- `planning.runs[]`、並行上限、排隊、獨立子資料夾、單獨停止、換 AI 接手、舊任務檔相容。
- 代理面板與對話中的需要處理提醒。
- 驗收：fake CLI 模擬兩個無相依項目並行、一個有相依項目等待；一個代理失敗不影響另一個；停止與重啟後狀態正確；並行寫入不互相覆蓋；revision 與 409 行為不退步。

**階段 3：專案學習筆記。**
- 依第十節產生與更新；保留使用者手寫內容；一鍵存到 Obsidian Vault。
- 驗收：狀態變化後筆記更新；手寫區塊保留；未驗證項目不被寫成已驗證；決策與理由正確對應紀錄。

**階段 4：成果預覽、判斷卡與上手引導。**
- 簡報逐頁預覽與針對頁面的修改意見、資訊整理出處、判斷決策卡、下載格式、首次啟動引導、白話錯誤。
- 驗收：以 `examples/lab/02-mini-deck.md`、`04-data-report.md`、`06-policy-faq.md` 類型的虛構任務用 fake CLI 跑完整流程；至少一次真實 CLI 端對端冒煙測試並記錄（不得以 fake 結果代替）。

**每階段都需：** `npm test` 全綠、新增功能有測試、使用者可見文字為繁體中文白話、README 與教學同步更新。

## 十四、不做的事

- 不做雲端多人版、帳號系統或付費機制。
- 不讓 AI 自動修改使用者的程式碼 repo 或系統設定。
- 不加入 runtime 依賴或前端框架。
- 不以 AI 自評、exit code 0、檔案存在代替人工驗收。
- 不宣稱未經真人或實機驗證的體驗已經完成。

## 十五、回報方式

PR 說明包含：

1. base commit、head commit、完成的階段。
2. 每項需求的狀態：已實作／已自動測試／已瀏覽器檢查／待真人驗證／未做與原因。
3. 測試結果（完整輸出摘要）與瀏覽器檢查的尺寸與情境。
4. 與現有資料格式的相容性說明，以及升級前是否需要備份。
5. 已知限制與下一步建議。
6. 截圖只用虛構資料。
