### Mentor 原本的產品知識

Mentor 是本機優先的多 AI 工作台。核心概念是任務檔作為正本，AI 接手前讀取目標與限制，停止後寫回結果；人負責決策與驗收。還包含 A–F 教練流程、回饋、學習日記與主動回想。

既有設計重點（請核對實際 checkout）：

- Task：目標、邊界、現況與下一步。
- Decision：選項、依據、代價與未知，必須由人明確決定。
- Evidence：機器檢查與人工確認分離。
- 任務 Markdown 包含人可閱讀內容與 `awc:begin`／`awc:end` 之間的產生區塊；不要破壞序列化契約或覆蓋區塊外的人工筆記。
- 交接回報使用 TASK_ID、BASE_REVISION、STATUS 等欄位；保留版本核對，DONE 不等於通過人工驗收。
- A 任務卡、B 追問、C 大綱、D 執行、E 審閱、F 修改，各階段權限不同。
- Codex／Claude Code／Copilot 透過已安裝且登入的 CLI 呼叫；是否可用須實測，不能假定外部環境具備。
- 預設資料位於 `vault/`、`outputs/`，也可指定 MENTOR_HOME；這些使用者資料不得作為 fixtures 或 PR 內容。
- 原生 Obsidian 整合、Theme、自動交接等能力是否存在，由實際 checkout 決定；規劃不可當成現況。

## 一、先理解目前真正的痛點

目前已知問題：

1. 使用者提出需求後，不容易確認 AI 是否理解正確。
2. 進度更新經常描述「AI 正在忙什麼」，沒有說清楚成果變化。
3. 任務、決策、成果、來源與歷史分散，使用者必須自行拼湊。
4. 功能與設定太多，使用者不知道現在該做哪一件事。
5. 太多表單要求使用者從空白開始填寫。
6. AI 能提出建議，卻未必能把建議準備成可以確認執行的方案。
7. 模擬、真實執行、機器檢查與人工驗收容易混淆。
8. 記錄很多，但下一個人或 AI 仍需重新閱讀聊天、找檔與猜進度。
9. Obsidian 的內容、Theme、範本與 Mentor 的任務流程結合不足。
10. AI 上下文可能重複攜帶，增加 Token、等待時間與理解負擔。
11. README 與教學未必符合實際版本，難以建立正確預期。

曾出現的反例：
使用者希望改善 Obsidian Theme，AI 卻製作新的 Mentor Web UI。
即使新 UI 能操作、測試通過，仍然是做錯方向。

系統必須能及早暴露與修正這類偏差，而非只完整記錄偏航過程。

## 三、建立清楚的產品分工

Mentor 負責：
- 理解需求與準備方案。
- 任務執行與狀態。
- 等待使用者回答的決策。
- 多 AI 指派、交接與中斷復原。
- 成果版本、證據與驗收。
- 每輪工作摘要。

Obsidian 負責：
- 閱讀與編輯來源內容。
- 整理筆記、連結與知識。
- 閱讀成果與留下批註。
- 保存日常紀錄、決策與經驗。
- 在內容脈絡中啟動 Mentor 工作。

Theme 與範本負責：
- 改善閱讀、資料層次與內容美感。
- 讓相同類型內容有一致結構。
- 降低整理成本。

兩邊共用同一份任務權威狀態。
不得各自建立互相矛盾的狀態與待辦清單。

## 四、讓每輪工作都看得懂

每輪應有一張簡明的「本輪工作卡」，由實際狀態與證據產生。

必要內容：
1. 我理解你要的是什麼。
2. 這輪準備處理什麼。
3. 實際完成了什麼。
4. 成果在哪裡，可以如何打開看。
5. 做了哪些驗證，結果與限制是什麼。
6. 有哪些未完成、阻擋或理解變更。
7. 下一步由誰做、做什麼。

依工作進度逐步更新，不要一開始填入尚未發生的成果。

簡單操作可合併成一張卡，不強迫每輪填滿所有欄位。
詳細工具輸出放在展開區，不淹沒主要資訊。

「計畫做」「正在做」「實際做完」「已驗證」必須區分。
沒有證據時保留未知，不自動補成成功。

工作卡應連到檔案版本、差異、來源與驗證結果。
不能只是另一段無法核對的 AI 自述。

- 使用者原始要求。
- AI 的理解。
- 預期成果。
- 可以改與不能改的範圍。

## 七、讓整理成為有成果的工作

建立整理閉環：
發現待整理內容
→ AI 提出方案
→ 使用者預覽／調整
→ 套用
→ 回報結果
→ 可追溯與復原。

整理後應更容易找到與理解內容，而不只是資料夾更整齊。

原則：
- 優先補索引、連結與必要 metadata，再評估搬移。
- 區分來源、自己的理解與正式成果。
- 不強迫所有筆記走完同一套分類階段。
- 資訊不足或規則衝突時放入待確認。
- 保留來源與歷史。
- 檔案搬移與重命名需處理連結。
- 不以模型自評的精確分數冒充可靠機率。
- 正式規則的修改與一般筆記整理分開。

## 八、多 AI 製作與交接

跨 AI 的核心不是保存整段聊天，而是保存可繼續工作的狀態。

每次執行至少記錄：
- 任務與執行 ID。
- Provider 與模型；無法取得時標未知。
- 開始時的任務與成果版本。
- 允許讀寫範圍。
- 使用的來源。
- 實際修改與產出。
- 驗證結果。
- 未解問題與下一步。

接手包包含：
1. 原始目標與目前有效範圍。
2. 已確認決策。
3. 最新成果與版本。
4. 已完成與已驗證的部分。
5. 未完成、失敗與未知。
6. 不能改動的限制。
7. 必要來源與取得方式。
8. 下一個 AI 的具體任務。
9. 回報與驗收要求。

接手時確認原執行是否停止。
結果未知時，不直接假設失敗並重跑。
舊版本回報不得覆蓋新工作。
AI 說 DONE 只表示可供驗收，不表示使用者已接受。

先做可靠的循序接力，再評估平行執行。
平行執行必須有隔離的產出範圍與整併規則。

## 九、同一份狀態，提供三種閱讀方式

給使用者：
本輪變化、可看的成果、限制與下一個行動。

給接手 AI：
精簡但完整的目標、決策、版本、證據與下一步。

給追查者：
完整操作、執行輸出與歷史。

三者由相同權威資料產生。
不要各自生成三份無法相互核對的描述。
重要摘要需保留來源與版本。

## 十、Mentor UI 改善

先找出使用者完成工作的必要步驟，再決定頁面結構。

初始方向：
- 現在：只呈現需要人處理的事。
- 任務：目標、進度、工作卡與對話。
- 成果與知識：閱讀、驗收、引用與保留。

這是可調整假設，不是必須照抄的導覽。

要求：
- 一個明確主要行動。
- 設定與技術細節按需展開。
- 同一操作有相同命名與行為。
- 表單有合理預填、必要說明與驗證。
- 空白、載入、失敗、離線與中斷都有可理解的狀態。
- 不靠顏色區分重要狀態。
- 不把所有訊息都放成儀表板卡片。
- 不為了簡化而藏掉關鍵限制。
- 保留既有好用的互動，不任意全面重做。

## 十一、Obsidian Theme、範本與內容呈現

參考 letschips 公開圖片中的：
留白、字級層次、文件排版、Callout、表格與一致性。

建立自己的視覺語言。
不得複製付費 CSS、品牌、素材或文案。
使用開源內容時確認授權並保留聲明。

優先改善：
- 側欄與頁籤。
- 標題、內文與行距。
- Properties 與 metadata。
- 表格、清單與勾選項。
- Callout、引用、程式區塊。
- 來源、成果與版本提示。
- 淺色、深色與窄視窗。
- 閱讀模式與 Live Preview。

區分：
- Theme：整體外觀。
- Scoped snippets：特定筆記／範本樣式。
- Plugin：動態操作與資料。

不要把必須寫插件的能力假裝成 CSS 已完成。

首批範本：
工作首頁、任務、決策、AI 交接、成果驗收、
每日紀錄、每週回顧、來源筆記與知識卡。

範本應有可用示例，不只有空白欄位。
停用 Theme 或插件後，內容仍可閱讀。
不得因美化而改壞資料格式或既有筆記庫。

## 十二、Token 與執行效率

先量測浪費來源，不預先承諾節省比例。

檢查：
- 重送完整聊天或整個 Vault。
- 重複載入未變更的規則與文件。
- 工具輸出過長。
- 無關來源進入上下文。
- 摘要失真導致反覆返工。
- 可用程式完成卻呼叫 AI 的工作。

策略：
- 依階段載入必要內容。
- 文件先提供索引，按需取段落。
- 用版本／雜湊辨識更新。
- 分開穩定規則、任務狀態與臨時輸出。
- 接手包去重，保留來源。
- 大型工具輸出分頁。
- 摘要不得刪掉重要邊界、決策與未解問題。
- 整理、預覽與套用盡量分開，避免每個按鍵重跑整輪 AI。

相同任務比較：
請求次數、輸入／輸出 Token、可取得的快取 Token、
等待時間、費用、成果品質與重要資訊遺漏。

Provider 實測優先。
估算須標示方法；未知不可當成零。

## 十三、資料與數據應該好看，也可信

每個指標必須有：
定義、來源、期間、更新時間及實測／估算標記。

優先顯示：
待決策、阻擋、執行中、待驗收、
最後變更與可取得的使用量。

沒有資料時提供合理空白狀態。
不製造假熱力圖、假績效或假成本。
數據要能連回對應任務或紀錄。
圖表提供文字或表格替代。

## 十四、README 與教學

讓新使用者依序理解：
1. Mentor 解決什麼問題。
2. Mentor 與 Obsidian 如何分工。
3. 實際完成工作的畫面與流程。
4. 最短安裝與啟動。
5. 模擬體驗與真實 AI 執行差別。
6. CLI、登入、費用與平台限制。
7. 資料位置、權限與隱私。
8. 整理方案如何預覽、套用與復原。
9. 多 AI 如何交接與驗收。
10. 升級、備份、移除與常見問題。
11. 開發、貢獻、授權與已知限制。

教學必須實際走過。
截圖來自交付版本。
規劃中的功能不得列為已完成能力。
提供清楚的示範資料，不要求新手先接真實帳號。

## 十五、實作順序與驗收

第一階段：現況 Review
交付問題、保留項目、資料權威與優先順序。

第二階段：設計與契約
交付核心流程、畫面、Theme tokens、
工作卡、方案預覽、交接包與資料讀寫契約。

第三階段：完整小任務
優先用「改善 Obsidian 表格外觀」作為真實任務：
使用者提出需求
→ AI 顯示理解與方案
→ 預覽修改
→ 確認套用
→ 查看實際效果
→ 另一個 AI 接手處理剩餘項目
→ 人工驗收
→ 保存紀錄。

必須明確保留：
「調整 Obsidian，不能擅自改成重做 Mentor Web UI。」

另以 Mentor 自身文件測試：
整理入門指南、整理索引、產生接手包與每週回顧。

第四階段：失敗與復原
驗證過期方案、重複點擊、部分失敗、
同時編輯、舊回報、額度不足、中斷與服務重啟。

第五階段：文件與發行準備
交付可操作版本、原始碼、Theme／範本、
README、教學、相容性矩陣與驗證證據。

## 十六、真正的完成標準

找一位不熟悉專案的人，僅根據介面與工作紀錄確認：
- 他是否知道目前目標？
- 是否知道這輪實際改了什麼？
- 是否能打開正確成果？
- 是否知道哪些內容尚未驗證？
- 是否知道下一步由誰做？
- 是否能預覽並確認一個整理方案？

再讓另一個 AI：
不依賴完整聊天，只讀接手資料，繼續同一任務。

記錄實際需要補問、找檔、重講背景與修正方向的地方。
這些結果是改善依據，不可用漂亮畫面或單元測試數量代替。

如果沒有真人測試條件，明確標為尚未驗證。
不能自行宣稱新使用者已能理解。

## 十七、交付與回報

每階段回報：
- 解決哪個痛點。
- 改了什麼。
- 可在哪裡操作。
- 如何驗證。
- 還有哪些限制與待決事項。

不要每完成一個小修改就要求使用者確認。
需要產品決策時，先準備具體方案、預覽與代價。

不要只交付計畫、文件或模擬頁就停止。
也不要為了做得快，悄悄刪減真實整合、交接與復原要求。

最後交付：
1. Mentor 與 Obsidian 可操作版本。
2. Theme 與內容範本。
3. 每輪工作卡。
4. 方案預覽與確認套用。
5. 可追溯的多 AI 接手包。
6. 資料與復原設計。
7. 更新的 README 與教學。
8. Token 比較與測試證據。
9. 已知限制與未完成事項。
