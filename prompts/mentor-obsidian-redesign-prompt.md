### Mentor 原本的產品知識

Mentor 是本機優先的多 AI 工作台。核心概念是任務檔作為正本，AI 接手前讀取目標與限制，停止後寫回結果；人負責決策與驗收。還包含 A–F 教練流程、回饋、學習日記與主動回想。

既有設計重點（請核對實際 checkout）：

- Task：目標、邊界、現況與下一步。
- Decision：選項、依據、代價與未知，必須由人明確決定。
- Evidence：機器檢查與人工確認分離。
- 任務 Markdown 包含人可閱讀內容與 `awc:begin`／`awc:end` 之間的產生區塊；不要破壞序列化契約或覆蓋區塊外的人工筆記。
- 交接回報使用 TASK_ID、BASE_REVISION、STATUS 等欄位；保留版本核對，DONE 不等於通過人工驗收。
- A 任務卡、B 追問、C 大綱、D 執行、E 審閱、F 修改，各階段權限不同。
- Codex／Claude Code／Copilot 透過已安裝且登入的 CLI 呼叫；是否可用須實測，不能假定外部環境具備。
- 預設資料位於 `vault/`、`outputs/`，也可指定 MENTOR_HOME；這些使用者資料不得作為 fixtures 或 PR 內容。
- 原生 Obsidian 整合、Theme、自動交接等能力是否存在，由實際 checkout 決定；規劃不可當成現況。

## 一、背景與產品目標

Mentor 的核心價值是：
使用者不必在不同 AI 之間搬運背景，可以用同一份任務資料完成指派、決策、交接、驗收與經驗累積。

目前收到的反饋：
1. 整體 UI 複雜，使用者不知道第一步與下一步。
2. 功能分散，需要理解太多頁面、欄位與內部術語。
3. 與 Obsidian 的結合不夠深入，像另一套獨立工作系統。
4. 筆記、任務、成果與數據的呈現不夠精緻。
5. AI 上下文可能重複傳遞，Token 使用效率需要改善。
6. README 未能讓新使用者快速理解價值、安裝方式與實際流程。

目標體驗：
使用者主要在 Obsidian 裡閱讀、寫作、整理知識與查看成果；
Mentor 在需要時提供 AI 執行、待決事項、交接與驗收能力。

不要要求使用者先理解系統架構，才能完成第一個任務。

## 三、產品與資訊架構

以三個主要工作入口組織體驗：
- 現在：需要我處理什麼？
- 任務：正在做什麼，下一步是什麼？
- 成果與知識：完成了什麼，如何閱讀、引用與保留？

這是初始假設，可依盤點調整，但必須解釋原因。

設計原則：
1. 每個畫面有一個明確主要行動。
2. 首頁優先顯示待決策、阻擋與待驗收事項。
3. 模型、參數、執行細節與完整歷史按需展開。

7. 功能隱藏後仍需可找到，不能為了簡潔刪掉必要能力。

## 七、Token 使用效率

先找出實際浪費，再改善。
不得只把 Prompt 變短，就宣稱更有效率。

檢查：
- 每輪是否重送整段聊天或整個筆記庫。

- 接手包是否含過時、重複或無關資訊。
- 是否能依任務階段只讀必要內容。
- 是否有不必要的 AI 呼叫，可改用確定性程式處理。

建議策略：
1. 接手包保留目標、限制、已確認決策、來源、版本與唯一下一步。
2. 大型內容先提供索引，再依需求取得相關段落。
3. 使用內容雜湊與版本判斷更新，避免重複處理未變更內容。
4. 區分使用者原文、AI 摘要與已確認事實。
5. 摘要保留來源，重要約束不得因壓縮而遺失。
6. 限制工具輸出與歷史長度，必要時分頁讀取。
7. 若使用快取，說明適用範圍、失效條件與隱私邊界。

不以規劃中的功能作為已完成宣傳。

範本、Theme、插件與文件須能由公開原始碼重建。
核心功能不綁啟用碼或官方雲端。
外部 AI 與 Obsidian 本身的授權條件另行說明。

## 九、執行階段

階段 1：現況 Review
交付問題清單、現有流程與保留／調整建議。

階段 2：設計方案
交付資訊架構、核心畫面、Theme tokens、
Obsidian／Mentor 分工與資料讀寫契約。
先用 Mentor 自身文件形成完整範例。

階段 3：端到端實作
完成：
從 Obsidian 筆記建立任務
→ 明確確認範圍
→ AI A 執行
→ AI B 接手
→ 閱讀成果
→ 人工驗收
→ 保留經驗。

優先打通這條流程，再擴充其他畫面。
模擬資料可用於開發，但不可代替真實整合驗收。

階段 4：品質與效率驗證
測試關鍵失敗路徑，量測 Token，
檢查 Theme、不同視窗寬度、鍵盤與資料完整性。

階段 5：文件與交付
更新 README、教學、截圖、變更說明、
相容性矩陣與已知限制，提供可操作版本。

## 十、最低驗收條件

- 新使用者不用先讀架構文件，也能開始第一個任務。
- 首頁能清楚指出下一個需要人的行動。
- 在 Obsidian 內完成核心流程，不必反覆搬運內容。
- 新 AI 接手時，保留已確認決策與必要來源。
- AI 回報成功不會自動通過人工驗收。
- 額度不足、登入失效、中斷與結果未知不會被當成完成。
- 同時編輯、舊回報與服務重啟不造成資料覆蓋或重複執行。
- Theme 停用或插件移除後，原始筆記仍完整。
- Token 改善有可重現的比較，且未遺漏重要資訊。
- README 的啟動流程與功能聲明符合實際交付版本。

## 十一、回報方式

開始時先說明盤點範圍與發現。
每完成一階段，回報：
- 改善了哪個使用者問題。
- 具體改了什麼。
- 如何測試，證據在哪裡。
- 尚未完成或仍需確認的事。

不要用大量文件、漂亮截圖或測試通過數量代替完整流程。
不要為了達成指標而刪除必要資訊或縮小原本需求。

最終交付：
可操作版本、原始碼、Theme／範本、
README、測試證據、Token 比較與已知限制。
