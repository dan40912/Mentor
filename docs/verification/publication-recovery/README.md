# 隔離發布恢復的 Web 操作驗證

執行 `node scripts/demo-publication-recovery.mjs`，預設 4364，可用 PORT 指定空閒埠。資料建立於 .lab-home 的新目錄；不讀正式 Vault。runner 只會拋出測試錯誤，不能呼叫 provider。程式刻意在原成果移至備份後中斷，產生需要核對的狀態；不要把此腳本當正式服務啟動器。

本次實際操作：首頁「核對成果發布」→ 未勾確認時嘗試恢復（拒絕）→ 核對虛構原稿與候選、確認無 CLI 執行 → 勾選確認 → 恢復原成果 → 重載再讀紀錄。pending.png／restored.png 保留畫面，result.json 核對磁碟 hash、候選保留、工作仍 TODO、running=null。這是 AI 代理操作的 Web 測試，不是真人或原生 Obsidian 驗收。

| UI 檢視欄位 | 結果 |
| --- | --- |
| 使用情境 | 發布中斷後先核對，不能先執行 AI。 |
| 資訊與欄位 | 顯示發布狀態、候選與實際備份；確認原 CLI 停止後才能選擇恢復。 |
| 移除冗餘 | 待核對時隱藏自動、執行、改計畫與驗收控制；歷史保留可讀。 |
| 一致性 | 任務狀態、首頁建議、Web 與原生入口共用 publication 阻擋。 |
| 證據 | 實際 Web 截圖與磁碟 hash；414 項本機測試、10 runtime 比對通過。 |
| 驗收限制 | 原生 UI、鍵盤／讀屏、真人理解與真實 CLI 仍待驗收。 |
| 結論 | Web 隔離恢復流程通過；整體產品尚未驗收完成。 |

恢復後原備份已移回，畫面應顯示「原成果已恢復至成果目錄；原備份已移回」，不將歷史備份位置說成仍存在的檔案。候選與紀錄保持可追查；恢復不是任務完成。
